# Automatic deployment

Pushing to `main` releases the bot and all three media images together. Feature branches do not deploy. The updater keeps the existing database, secrets, mounts, limits and channel settings.

## Release flow

1. GitHub Actions runs typecheck, lint, build and tests, including the offline updater tests.
2. It builds Linux AMD64 bot, broker, FxEmbed and media-worker images from the exact committed source. Build contexts exclude `.env`, backups, dependencies and uncommitted files.
3. It publishes each image to GHCR with the commit SHA, records its immutable digest, and inventories the installed container packages.
4. Only after every build and inventory succeeds, it publishes a GitHub release named `main-<commit>`. The release has `caitlyn-release.json` and `caitlyn-installations.json` attached. There is no mutable `latest` image in this rollout path.
5. A TrueNAS cron task checks every five minutes. It accepts only a complete release for the current `main` commit, with the approved database migration fingerprint.
6. It downloads all four images and checks their revision labels and architecture. A temporary bot-image check imports the full bot entry point, then verifies database access and required tables without starting the bot, logging into Discord or writing data. This check has a 90-second limit and runs while the existing bot is still online.
7. If the app is still running with the same configuration and the worker is idle, it saves the previous app configuration, stops the app, applies all image IDs, and starts the app again.
8. It waits for healthy media services and the bot's completed Discord startup, then registers commands in the configured guild. Ordinary restarts do not register commands again. Global commands are not changed by this updater.

There is a brief outage while the app restarts. This is not a rolling deployment: running two copies with the same Discord token can process events twice. The database app is not stopped or replaced.

## GitHub setup

The repository workflow is `.github/workflows/ci.yml`. Its release job needs permission to write repository releases and GHCR packages. It uses the existing `CR_PAT` repository secret for registry login, passed through standard input. Do not put it in the workflow file. GitHub's job token creates the release.

Images are named from the repository, lowercased: `ghcr.io/<owner>/<repo>`, plus `-broker`, `-fxembed` and `-media`. The server needs registry credentials with read access if the packages are private. Package visibility is separate from repository visibility; see [GitHub's container registry documentation](https://docs.github.com/en/packages/working-with-the-container-registry/working-with-the-container-registry).

Release metadata is read from a **public GitHub repository** without an API token. Private repositories need a separately reviewed authentication extension. No server SSH key, bot token, database password or X account cookie is sent to GitHub Actions.

## Server setup

Use the existing Python 3, Docker and TrueNAS API client (the library shipped with `midclt`). No host pip/npm installation or GitHub runner is needed. The updater calls the local TrueNAS socket directly, keeping app configuration out of command-line arguments. The updater is a root-owned script because it controls the selected app through TrueNAS and Docker; its folder and configuration must not be writable by the bot or other users.

Create a dedicated directory outside the container mounts, mode 0700, owned by root. Its parent directories must not be writable or replaceable by unprivileged users. The mainframe uses `/root/.config/caitlyn-release-updater` on its writable root-home dataset, not the apps-owned runtime dataset. Copy `scripts/deployment/autoUpdate.py` there, mode 0600. Add `config.json`, also root-owned mode 0600:

```json
{
  "repository": "OWNER/REPOSITORY",
  "app": "caitlyn",
  "runtimeRoot": "/mnt/POOL/apps/caitlyn/runtime",
  "approvedMigrationHash": "THE_REVIEWED_64_CHARACTER_MIGRATION_HASH",
  "enabled": true
}
```

`runtimeRoot` is the existing protected runtime directory containing `bot`, `ipc`, `key` and `fx`. The updater expects the reviewed three-service layout generated by `scripts/deployment/compose.mjs`; additional services or changed security policy require review. It changes only the three running image IDs and the broker's media-worker image ID. Updating the Compose layout or updater itself is a separate operator task, not downloaded host code execution.

Compute the migration fingerprint from the checkout **only after verifying that those migrations are applied to the selected database**:

```bash
node --input-type=module -e 'import {migrationFingerprint} from "./scripts/deployment/releaseManifest.mjs"; console.log(await migrationFingerprint("migrations"));'
```

Do not copy a new hash into the configuration just to silence a database-change warning. Back up and test missing migrations first. Automatic updates never run SQL migrations, restore dumps, or merge local testing data.

Create one [TrueNAS cron task](https://api.truenas.com/v25.10/api_methods_cronjob.create.html), running as root, every five minutes, with the command:

```text
/usr/bin/python3 -B /root/.config/caitlyn-release-updater/autoUpdate.py /root/.config/caitlyn-release-updater/config.json
```

Replace the paths with the actual protected directory. Do not add a second task if one already exists. A process lock also prevents overlapping runs. The app must already be running; the updater will not start an app that an operator stopped. Keep Watchtower disabled for these services.

Keep a private backup of this updater directory and verify its task/path after a TrueNAS upgrade or boot-environment change. The server-side script does not replace itself when application images are updated.

Add `--check` to run the release metadata checks without pulling images, registering commands or changing services. The normal command applies an eligible release. A missing initial release is a quiet no-op.

## Failure handling and rollback

- A failed build never publishes a complete release, so the running version stays in place.
- Missing images, unexpected repositories, bad hashes, new migrations and failed preflight checks stop the update before the running app is touched.
- A busy worker defers the update. An app stopped or edited during the download is left alone. Changes in the final short stop/update window still require operator coordination.
- Failed startup or guild registration triggers restoration of the saved app configuration, readiness checks and old guild command registration. The failed commit is blocked from automatic retries; a new commit can release a fix.
- The updater logs each TrueNAS job number and checks that same job for up to five minutes. A missed status check is retried; the stop/update/start request itself is never repeated blindly. If its job number or final result is still unknown, the updater does not start a competing rollback. It leaves its saved state marked unfinished and pauses further updates for inspection. A failed rollback also remains unfinished.
- No database rollback or image/volume pruning is performed. Preserve post-release database writes. Temporary worker leftovers require explicit inspection; the updater never deletes them automatically.

The updater directory contains `updates.log` (1 MiB plus three rotated files), `state.json`, and per-release folders with `previous-compose.json` and `installations.json`. Logs use UTC and short status messages, never raw command output, credentials or media content. These are deployment logs on the server, not automatically forwarded to Discord. Existing bot logs keep their configured private Discord destination.

To pause updates, disable the TrueNAS cron task or set `enabled` to `false` in its private configuration. To recover an unfinished update, inspect the recorded phase, TrueNAS jobs, current containers and saved configuration before changing state. Do not delete the state file or clear `blockedRevision` as a substitute for fixing the failure. Do not restart the local bot until the server bot has stopped.

## Installed software

Every release attaches an exact container package inventory: OS packages, npm packages with versions/paths, and extractor Python packages. The updater verifies the inventory hash and saves it beside the previous app configuration. Pulling these images installs no packages on macOS or the TrueNAS host; container dependency changes are still listed in the inventory.

The initial mainframe installation is recorded in [mainframe deployment](mainframe-deployment.md) and [its package inventory](mainframe-installations.md). Use the newer release's attached inventory for later deployments.
